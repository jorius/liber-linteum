**Where it is.**

- **Branch:** `feat/enc-e4`, HEAD `54247d1`. It is rebased onto the E3 head `4f53f74` (E3 is already merged to `main`). Nothing is merged and nothing is pushed.
- **Plan:** `docs/superpowers/plans/2026-10-20-enc-e4-encrypted-vault-ui.md`.
- **Spec:** `docs/superpowers/specs/2026-10-20-encryption-design.md` §6 (locking), §7 (passphrase), §8, §12 (Beta label) and §16 (localStorage audit; E4 added its own subsection).
- **Ledger and reports:** `.superpowers/sdd/2026-10-20-enc-e4-encrypted-vault-ui/` (`progress.md`, `task-N-report.md`, `final-fix-report.md`). The folder is git-ignored, so it exists only in the worktree that ran E4.
- **Constraint still in force:** no Mac or Windows bundles until E3 and E4 are both merged (the maintainer, in the E3 hand-off).

**What E4 is.** E3 built the encrypted storage and the commands, with no screens. E4 is every screen and behaviour on top of them:

- Creating an encrypted vault (from Welcome and from the Vault menu), including the recovery key step.
- The Unlock screen (passphrase or recovery key), and the lock icon in the recent-vaults list.
- Locking: menu item and shortcut, idle timer, sleep, screen lock.
- Settings → Security: auto-lock time, change passphrase, new recovery key, and the "Couldn't read" list.
- The prompt shown when the recovery key was replaced on another device.
- A confirm before opening an attachment (a decrypted copy goes to a temporary folder).
- A check that nothing about an encrypted vault leaks into `localStorage`.

Everything encryption-related carries a visible "Beta" label (spec §12).

**One thing to know first.** The final whole-branch review (opus) found a real problem class that two shortcut re-reviews had missed. See section 5.2. It is fixed in `54247d1`. The opus re-review of `54247d1` confirmed C1/I1/I2/I3 and the minors, and found one new Important in the fix itself: the voided-key prompt was parked under whatever vault was open, not its own, so switching to a plain vault showed it there and lost it for the voided one. ## 2. How to verify

All commands run from the worktree root. The shell default is Node 20, which makes vitest fail. Use Node 24:

```sh
export PATH="$HOME/.nvm/versions/node/v24.21.0/bin:$PATH"
node --version   # v24.x
```

### 2.1 Unit tests (vitest)

```sh
pnpm --filter @liber/desktop exec vitest run --maxWorkers=2
```

Expect 159 files and 1803 tests at `54247d1`. The E4 files are in `apps/desktop/src/features/encryption/` and `apps/desktop/src/stores/`. For a quick look only at E4:

```sh
pnpm --filter @liber/desktop exec vitest run src/features/encryption src/stores
```

### 2.2 The E4 end-to-end spec (Chromium and WebKit)

The spec is `apps/desktop/e2e/e4-encryption.spec.ts` (30 tests = 15 per engine). It runs against the built UI with the IPC mock (`e2e/ipcMock.ts`, option `encrypted: {…}`), not against the real Rust backend. Build first, then run:

```sh
pnpm --filter @liber/desktop exec vite build
LIBER_E2E_PORT=4402 \
PLAYWRIGHT_BROWSERS_PATH=<scratchpad>/pw-browsers \
  pnpm --filter @liber/desktop exec playwright test e2e/e4-encryption.spec.ts
```

- `LIBER_E2E_PORT` picks the preview-server port. Use a free one; E4 used 4402 so it did not clash with other worktrees.
- `PLAYWRIGHT_BROWSERS_PATH` points at the downloaded browsers. If you have the browsers installed in the default place you can leave it out.
- Skipping `vite build` runs the tests against a stale build. This is the most common cause of a surprising failure.
- The WebKit run is wired through `testMatch` in the Playwright config, added in Task 2.

## 3. Manual test script for the maintainer

The e2e suite uses a fake backend, so only a real run proves the pieces work together with E3's Rust. Run this in the built app (or `pnpm tauri dev`). Use a **throwaway empty folder** for each vault. Never test with your real notes.

Do not use osascript or send key codes to your Mac to drive this (your standing rule). Type the keys yourself.

Write the recovery key somewhere safe for the duration of the test (a scratch text file is fine; it is a throwaway vault).

### 3.1 Create from Welcome

1. Quit any open vault so you land on Welcome (or Vault → Close Vault).
2. Find the **Encrypt this vault** switch, with a **Beta** pill. It is off by default and is not remembered between visits.
3. Switch it on, then create a vault in an empty folder (the normal New Vault path).
4. Step 1, passphrase. Type fewer than 12 characters: Continue stays off and the hint reads "At least 12 characters." Type `blue cat sun`: it should rate "fair" (spaces count as symbols). Type a long unrelated-words passphrase: "strong".
5. Type a different text in Confirm and press Tab. "The passphrases don't match." should appear when you leave the field, not while you type.
6. Tick **Show passphrase** and check it reveals both fields. Untick it. Fix the confirm and press Continue.
7. Step 2 shows "Setting up encryption…". It takes a second on purpose (key stretching).
8. Step 3, your recovery key: `LIBER-` plus 14 groups of 4 characters. Press **Copy**. The note "Copied — clear your clipboard once you've stored it." appears. Save the key.
9. Click **I've saved it**. The dialog asks for two groups (for example "group 3 and group 9") in ascending order. **Done is off.** Check that a screen reader or hover hint says "Done turns on once both groups match your key."
10. Type a wrong group. Done stays off. Type the right ones. Done turns on. Typing in lower case, with spaces or hyphens inside the group, or `O` for `0`, is accepted.
11. Press **Done**. You land in the vault shell; focus should be in the editor (or the tree if no page is open).
12. Escape and clicking outside must **not** close the dialog on steps 2 and 3.

### 3.2 Create from Vault → New Encrypted Vault…

1. With a vault open and an unsaved edit (turn auto save off in Settings first, then type in a page without saving), open **Vault → New Encrypted Vault…**.
2. The unsaved prompt must come **first**, before the folder picker. Choose Save.
3. Pick an empty folder, then run the same dialog as in 3.1.
4. While the recovery key (step 3) is showing, press ⌘, and use the Settings menu item. Settings must **not** open and must not replace the dialog. Try ⌘O as well; it must do nothing.
5. Try picking a non-empty folder. You get an inline refusal in the dialog (not a toast). There is no "pick another folder" button; see 6.6.

### 3.3 Write pages, then lock

1. Create a folder and three pages with text. Add an image or an audio recording (3.9). Pin one as a favourite.
2. Make an unsaved edit with auto save off, then press **⌥⌘L** (Vault → Lock Vault).
3. Expected: the edit is **saved without a prompt** and the Unlock screen appears. The shell was inert (not clickable) during the lock. No page names, toasts, or dialogs remain on screen.
4. Check the Vault menu: **Lock Vault** is enabled only while an encrypted vault is open. On Welcome or in a plain vault it is greyed out.

### 3.4 Unlock with the passphrase

1. The Unlock screen shows a **Beta** pill, a passphrase field and "Use recovery key instead".
2. Type a wrong passphrase and press Unlock. Expected: "That passphrase doesn't open this vault. If you're sure it's right, this vault's key file may be damaged." The text stays in the field, selected and focused. Nothing counts your attempts. (The second sentence is deliberate: E3 reports a damaged header as "wrong secret" too.)
3. Type the right passphrase. "Unlocking… (this takes a second on purpose)" shows, then the vault opens with your pages, including the unsaved edit from 3.3.
4. If the vault had recordings cut by the lock, a recovered-clip toast appears (see 3.9).

### 3.5 Unlock with the recovery key, typed loosely

1. Lock again. Choose "Use recovery key instead".
2. Type the key all lower case, with spaces between groups, and one `0` typed as `O`. It should unlock. (The UI passes your text through; E3's parser is the forgiving part.)
3. Try a clearly wrong key: "That recovery key doesn't open this vault." Try junk: "That doesn't look like a recovery key."
4. **Back** on the Unlock screen returns to Welcome. Open Search and Global View afterwards: nothing from the locked vault should be there.

### 3.6 Idle lock

1. Settings → Security → **Lock after inactivity**: choose **1 minute**.
2. Leave the app untouched for just over a minute. It locks and the Unlock screen shows. Moving the mouse once per second counts as activity; keystrokes, clicks and wheel too.
3. Repeat, but start a recording and leave it running past a minute. The lock must be postponed (it retries a minute later) while the take is in progress.
4. Also check "Never" and 15 minutes (the default). When you are done, put it back to what you like.
5. Known gap: input in a **loose file window** does not reset the timer (6.1).

### 3.7 Sleep and screen lock (the macOS check from E3)

This is the manual check the E3 hand-off left for E4. No real sleep or screen lock has been exercised by any test.

1. **Screen lock with another app in front.** Open the encrypted vault, then bring a different app to the front. Lock the screen (Control-Command-Q). Wait about 10 seconds, unlock the Mac. Expect the vault to be on the Unlock screen when you return. This checks E3's `DeliverImmediately` fix.
2. **Sleep.** Make an unsaved edit (auto save off), sleep the Mac for over 30 seconds, wake it. Expect the Unlock screen within about 5 seconds of wake, and the edit saved.
3. **Known gap:** the vault locks **after** wake, not before sleep. Keys stay in memory through sleep (6.10).
4. Record what you see. If the front-end could not save (a failed save aborts the lock), see 6.4.

### 3.8 Settings → Security

Open Settings; **Security** has a Beta pill in the nav and the title.

1. **Change passphrase.** Enter the wrong current passphrase: the error shows on that field and all three fields clear. Enter the right one with a new passphrase and a matching confirm: toast "Passphrase changed". Lock, then try the **old** passphrase (must fail) and the **new** one (must work).
2. **New recovery key.** Press "New recovery key…". Settings closes and a dialog asks for your passphrase, then shows the new code with the same two-group check. "Your old recovery key stops working." Check this by locking and trying the old key (must fail) and the new key (must work).
3. **The code survives a lock.** With the new code showing, trigger a lock (⌥⌘L, or let the idle timer fire). The code dialog must stay, with focus on it, over the Unlock screen. After you confirm and press Done, you land on the Unlock screen with focus in its field.
4. After Done on a normal (non-void) new key you land in the **shell**, not back in Settings (6.9).
5. **Voided recovery key.** Hard to test by hand: it appears when another device replaced the recovery key. If you can set up two devices over a synced folder, change the recovery key on device A, open the vault on device B. B shows "Recovery key replaced" and one button, "Make a new recovery key". It cannot be dismissed. Lock while it is up and unlock again: the prompt must come back.
6. **Conflict message.** If two devices change keys at once, expect "Another device changed this vault's keys. Lock the vault and unlock it again, then try."

### 3.9 The "Couldn't read" list

1. In Settings → Vault settings, an encrypted vault shows a **Couldn't read** section only when something is unreadable.
2. To provoke it, lock the vault, drop a stray file with a nonsense name into the vault's data folder in Finder, and unlock. The list shows the entry and a Reveal in Finder action. Entries are never deleted or renamed. The hint says export arrives in a later version.
3. The section is absent in a plain vault, and absent in an encrypted vault with no unreadable entries.

### 3.10 Opening an attachment (decrypted copy)

1. Attach a PDF or image to a page in the encrypted vault, then open it with the system viewer ("Open").
2. A confirm appears: "A decrypted copy will be written to a temporary folder until the vault locks." Buttons: **Open copy** and **Cancel**.
3. Open copy. The file opens in the other app. Lock the vault: the temporary copy should be gone (E3 sweeps it).
4. In a **plain** vault the old behaviour is unchanged: no confirm, the file opens straight away.

### 3.11 Recordings in an encrypted vault

1. Start a recording, stop it, check the clip plays after the page saves and reloads.
2. Start a take and lock (or sleep) mid-recording. Unlock. Expect a recovered-clip toast and a `…-recovered.wav` beside the page's attachments.

### 3.12 What "Beta" means

The pill appears on the Welcome switch, the create dialog, the Unlock screen, and the Security category. Per spec §12, the feature is labelled beta until an external review of `liber-crypto` and the format spec is done (the review scope names the unaudited crates `aes-siv`, `ml-kem` and `argon2`, and our composition of them). So "Beta" means "not externally reviewed yet", not "may lose data". The spec also forbids claims such as "military grade" or "unbreakable". Later work (convert, rotation, keyring, Touch ID) is E5 to E7. Check that the surrounding copy says enough for a user to understand this.

### 3.13 Spanish copy

All strings exist in `en` and `es`, but the Spanish was written by the agents and **never read by a native speaker**. Switch the language to Spanish and read, at least: the Welcome switch, the passphrase and strength lines, the whole recovery key step (including "Hecho se activa cuando los dos grupos coinciden con tu clave."), the Unlock screen errors (including the new "Si estás seguro de que es correcta, el archivo de claves de esta bóveda puede estar dañado."), the rollback-memory reset dialog, and Settings → Security. Note tone as well as grammar: warnings about "we can't recover it for you" must sound serious, not cute.

### 3.14 What to report

For each step, note pass or fail. Anything marked "must" that does not behave is a bug to log against E4. Anything described as a known gap in section 6 is expected.

## 4. Architecture map

All paths are under `apps/desktop/` unless stated.

### 4.1 The vault store (`src/stores/vaultStore.ts`)

| Piece | Role |
|---|---|
| `status: 'locked'`, `lockedPath` | A vault that exists but needs a secret. `open()` of an encrypted vault answers `locked` from E3 and lands here, with no toast |
| `unlock(secret)` | Sets `unlocking` (so `App` keeps the Unlock screen mounted while the vault opens). Runs `withProgress` with `quiet`, so a wrong secret is shown inline, not toasted |
| `lock(reason)` | Saves every dirty page without asking (`savedEverything({ask:false})`), re-checks for new dirty pages right before `vault_lock`, aborts if a save fails, then `dropVault()` and `locked`. The `locking` field makes the shell `inert` for the whole lock |
| `lockedByBackend(path)` | Backend locked first (`vault:locked`). Idempotent, no IPC. Ignored while our own `lock()` runs |
| `cancelUnlock()` | The Unlock screen's Back button |
| `createEncrypted(path, pass)` | Quiet create; has a `creating` flag; catches a throw and returns it as an error. A created vault still returns its code if opening it failed afterwards |
| `leaveVaultUi()` | Called by `dropVault` (lock, lockedByBackend, Close), `cancelUnlock`, and `opened()` whenever a different vault (plain or encrypted) replaces the one open or at the door. Keeps held code dialogs and the app-level `notionImport` / `scratchpadSetup`. See 4.2 |
| `voidPending` | In-memory only. The root of the voided-key prompt that leaving took down (the prompt's own `root`, never the vault open now); `opened()` shows the prompt again only for that root. Lost on quit: E3 reports a void only once |
| `opened()` | Opens the `recoveryVoid` prompt if E3 says so (or if the root is parked); toasts recovered clips through `features/audio/announceRecovered.ts` |

`src/stores/leaveVault.ts` is a small leaf module with `onLeaveVault(fn)` and `clearVaultCaches()`. Features register their content caches at load (link completion page cache, Mermaid diagrams, spell cache, live-preview HTML). It is a leaf so nothing imports the vault store in a cycle.

### 4.2 Sticky dialogs (`src/stores/uiStore.ts`)

Some dialogs must not vanish by accident because they hold something the user cannot get again.

- `openDialog(d)` now **returns a boolean** and **refuses** to replace a sticky dialog. `isSticky()` is true for:
  - `recoveryVoid` (always),
  - `newRecovery{fromVoid}`,
  - a `createEncrypted` or `newRecovery` whose `held` flag is set. `hold(true)` is set when the call starts (the backend replaces the key during the call) and released on failure, unmount or `closeDialog`.
- A refused caller behaves as if the user cancelled. The only callers that wait for an answer are `confirmUnsaved` (resolves `false`) and the bin's keep-both prompt (`false`). Every other `openDialog` caller is fire and forget.
- The `held` dialogs also survive `leaveVaultUi`. The non-held ones do not (a lock closes them). That asymmetry is deliberate: a code on screen is never lost to a lock; a path-bearing dialog never survives one.
- Dialog types added: `createEncrypted`, `recoveryVoid{root}`, `newRecovery{root, fromVoid?}`. The prompt renders only while its own `root` is the open vault.
- `openCreateEncrypted` refuses while `unsaved`, `binClash`, `notionImport` or `scratchpadSetup` is showing (each is waiting for an answer or running).

### 4.4 Auto lock (`autoLock.ts`)

- Idle timer of `settings.autoLockMinutes` (default 15, allowed 1 to 60, `null` is never). Reset by keydown, pointerdown, wheel, and pointermove (throttled to 1 per second).
- A recording in progress (`useRecorderStore.phase` is `recording` or `starting`) re-arms the timer one minute later. A failed idle lock also re-arms one minute later.
- `onLockRequest` (sleep, screenLock) locks at once, even during a recording; E3 keeps the take.
- `onVaultLocked` calls `lockedByBackend`.
- `Ctrl/Cmd+Alt+L` is handled in JS too, because non-macOS has no native accelerator. On macOS both fire; `lock()` is guarded, so the double is harmless.
- Calls `menu_set_lock_enabled(true/false)` on mount and cleanup.

### 4.5 `CreateEncryptedHost` and the entry points

- Welcome: the "Encrypt this vault" switch (off, not remembered; Cmd/Ctrl+N honours it).
- Vault menu: `shellMenu.ts` handles `menu:vault` ids `lock` and `newEncrypted`. `newEncryptedVault` asks `confirmUnsaved` first, then the folder picker, then opens the dialog.
- `openSettings` opens only while a vault is open; on Welcome or Unlock it does nothing. File windows always open it. ⌘, over Search works.

### 4.6 Rust: `src-tauri/src/menu.rs`

- Vault menu is now: Open Vault…, New Encrypted Vault…, **Lock Vault** (Alt+CmdOrCtrl+L, disabled at start), Close Vault.
- `vault_action(id)` maps menu ids to the front-end action names.
- New command `menu_set_lock_enabled(bool)`. Registered in `lib.rs`, `build.rs`, `capabilities/main.json` and the generated permission toml. `tests/menu.rs` was updated for the new menu.

### 5.2 The honest note on the controller-only re-reviews

For speed, the re-reviews of Tasks 4 and 5 were done by the controller reading the fix diffs, not by a second reviewer. Each finding mapped to a visible hunk, so they were accepted. Those reviews looked at whether each fix was **present**. They did not ask what happens to the new "sticky" dialogs when the vault is **left**: lock, Close, switching vaults, the idle timer.

The final opus review did ask that, and found:

- **C1:** locking while the voided-key prompt was up stranded an undismissable dialog over the Unlock screen, and the warning was lost for good (E3 reports a void once).
- **I1:** the Settings new-recovery code lived in the Settings dialog's local state, so a lock, ⌘O or an unsaved prompt lost it **after** the header had already changed.
- **I2:** a lock left paths in `uiStore.dialog`, toasts and the bin in memory or on screen.
- **I3:** the Unlock wrong-secret copy contradicted E3's ruling #11 (a header MAC failure reports `wrongSecret`).

The controller accepted the finding. The fix wave in `54247d1` covers all four, with tests written first. Lesson for next time: any change to a "cannot be dismissed" surface needs a review that asks about teardown, and recovery-code paths get no controller-only re-review. 

**Second review of `54247d1` (opus).** It confirmed the four findings and the minors fixed, and found one new Important in the fix: the voided-key prompt was parked under `info.root` (the vault open at the time), the dialog did not say which vault it belonged to, and switching to a plain vault never ran `leaveVaultUi`. Unlock a voided `/v`, ⌘O a plain `/p`: `/v`'s prompt showed over `/p`; Close parked it under `/p`, so it came back over `/p` every time and never for `/v`. Fixed in the second pass: the dialogs carry their `root`, parking uses it, and `opened()` leaves the previous vault's UI whenever another vault replaces it. Also folded: a Cancel after a failed in-flight key call during a lock no longer leaves an invisible prompt that Back drops; Vault → New Encrypted Vault no longer replaces a pending question or a running import; four more module-level holders (`pageModel`, `blockCommands`, `ItemIcon`, `gvStore.shownAt`) empty on leave; an aborted lock gives focus back.

**Known limit: quitting while the prompt is parked.** `voidPending` lives in memory only (never storage: it is a vault path). If the app quits while a voided prompt is parked, the warning is lost: E3 reports a void only on the unlock that merged the headers. Making a new recovery key from Settings → Security still works; it just isn't prompted.
