**Where it is.** Branch `feat/enc-e1` is merged into `feat/r3` (merge 1ab83b1, on top of the Liber Linteum rename). Nothing is merged to main and nothing is pushed.

- **Format (byte level):** `docs/security/vault-format-v1.md`.

## 1. What exists

A pure-Rust crate, `crates/liber-crypto`, with no file system access and no Tauri. It contains:

| Module | What it does |
|---|---|
| `keys` | secrets (heap-allocated, zeroized, mlock'd) and the HKDF-SHA-512 subkeys |
| `recovery` | recovery codes: `LIBER-` plus Crockford base32, with a checksum |
| `kdf` | the Argon2id passphrase KEK. Calibrated defaults 256 MiB / t=3 / p=4; caps 1 GiB / 32 / 16 |
| `slots`, `header` | the vault header `liber-vault.json`, MAC'd canonical JSON. Covers slots, epochs, rotation with a retiring key, merge tombstones and `MergeOutcome` |
| `keyring` | X-Wing hybrid KEM (draft-06), the enrolled-vault commitments, `keyring.liberk` |
| `stream` | STREAM file contents: chunked AES-256-GCM in 64 KiB chunks; an append-only writer that is poisoned after an I/O error; a seekable reader; salvage |
| `names` | AES-SIV names with four AD headers (vault_id, epoch, parent, kind). Folder ids live inside folder names. Covers long names (`.liberl`/`.libern`) and sync-conflict suffixes |
| `vectors` | the frozen v1 vectors, plus an independent Python reader (`tests/xcheck/xcheck.py`, which needs `cryptography`; otherwise it SKIPs) |
| `fuzzing` | panic-only entry points with a proptest smoke test. The cargo-fuzz targets need nightly, which isn't installed; they have not been built yet |

## 2. How it was built and reviewed

The crate was built task by task with subagents. Each task got a fresh implementer, then a spec-and-quality review, then fix rounds with scoped re-reviews. Then:
1. A whole-branch review by Opus.
2. One fix wave, which closed I1 and I2 (below).
3. A scoped re-review, which said "ready to merge".

The frozen vectors are byte-identical from Task 7 to now.

The three findings closed at the final review:
- **I1:** the header re-MAC'd content it had never verified, which could permanently lock a user out.
- **I2:** public mutable fields let callers skip the safety checks.
- **The writer-poisoning test:** a test that the writer refuses to continue after an I/O error. Without that refusal, a retry could reuse a GCM nonce.

## 5. What E3 (encrypted storage) must do, from the reviews

- **Header rollback.** Persist the highest epoch seen per `vault_id`, app-side, and refuse or warn on a lower one.
- **Keyring public keys.** Only wrap a vault key to a keyring public key from a keyring file the app has unlocked.
- **Names.** Cap plaintext names at 255 bytes; `encrypt_*` already enforces this. Before joining a decrypted name to a path, require exactly one `Normal` path component; this matters on Windows (`C:x`, alternate data streams). Limit how much of a `.libern` side file is read.
- **Torn files.** A file torn mid-chunk reads as `Authentication`. Don't call that "tampered" outright.
- **Recordings.** Write takes into the vault, append-only (spec §4.2). Recover them at the vault's next unlock.
- **Merges.** On `MergeOutcome.local_recovery_dropped`, tell the user their recovery code is void and offer `new_recovery`. This is E4 UI work.
- **CI.** Before the first `REGEN`, or before E3 reaches main, add a CI job that installs `cryptography` and makes a SKIP of the Python cross-check a failure.
